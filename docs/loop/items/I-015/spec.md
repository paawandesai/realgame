## Facts from 3dbd332 this spec relies on

- **The game clock is clamped to 0.05 s per frame.** `control`, `aim_and_cast`, `projectiles`, `sync_visuals` (all in `main.rs`) and `fx::update_fx` each start with `let dt = time.delta_secs().min(0.05);`.
  - So below 20 fps, movement, the 0.3 s cast cooldown, the 0.3 s `cast_queue` expiry, projectile flight, beams, recoil, caption age and particle emission all run slower than the wall clock.
  - `chem_tick` runs in `FixedUpdate` at `chem::DT = 1/30`, driven by Bevy's `Time<Virtual>`, whose default `max_delta` is 250 ms. **The chemistry (fire spread, greenhouse heating) therefore keeps wall-clock speed down to 4 fps, while the player and spells slow down below 20 fps.** At 10 fps a fire spreads at full speed while the player walks at half speed and every spell takes twice as long to land. That is a correctness bug on slow school hardware, not only in the cloud.
  - In the cloud the effect is extreme: on the software GPU the frame interval is 0.4–1.5 s (`?low`) and 1.3–3.1 s (default), so the player moves at 3–12% of real speed. The qa persona's "2.5 s of W barely moved me" (nightly panel, turn 14) and the 13yo's `key w 2000` moving 0.5 m both follow from this. The planner reproduced it: holding `move 0 1` for 50 s of wall time at about 2.6 fps moved the player about 3 m per 5 s instead of 25 m.
- **`Player::step` is one explicit Euler step with axis-by-axis push-out.** It collects `colliders.solid(chem)` into a new `Vec` on every call. With `WALK = 5`, `SPRINT = 8.5`, `RADIUS = 0.35`, a step of 0.25 s moves 2.1 m on one axis, which passes straight through the greenhouse's 0.1 m glass panes (`pane(..)` at `x = ±8`, `world.rs`). So raising the clamp needs substeps.
- **Why the perf workload was incomplete (all of default@1x, default@4x, low@4x invalid in nightly 1).** Each `spellAt` step in `perf.mjs` queues `cast` and waits at most 6000 ms of wall time for `casts` to grow. The cast fires only when `game.cooldown <= 0`, and the cooldown (0.3 s) falls by 0.05 per frame. After the previous cast it needs about 5 more frames, which is 7–15 s of wall time at the cloud's frame intervals. The queued `cast` also expires after about 0.35 s of game time (7 frames). So casts time out. Nothing in the chemistry is broken: low@1x, whose frames were fastest, was valid in nightly 1, and on a quiet machine both low@4x (483 ms frames) and default@4x (1.4 s frames) were valid. **Workload validity therefore depends on the frame interval, which depends on machine load**: the same artifact passes or fails depending on what else runs. The clock fix (A) and the frame-aware timeout (D1) each remove that dependence.
- **The release profile optimises for size:** `crates/bevy-client/Cargo.toml` `[profile.release]` has `opt-level = "z"`, `lto = "fat"`, `codegen-units = 1`, `strip = true`. A `release-speed` profile (`opt-level = 3`) exists but `build-web.sh` never uses it. Brotli total is 3.55 MB against a 15 MB bar.
- **`?low` keeps FXAA on.** `read_settings`: `aa` absent gives `(msaa, fxaa) = (!low, true)`. `?low` turns off shadows, bloom and fire point lights, and halves particle emission.
- **The scene is about 619 entities** (`STATS entities=619`): a 160-slot particle pool under `?low`, the 10-piece viewmodel, and one entity per scenery piece. Every `Builder::piece`/`block`/`tree`/`pane` call spawns its own `Mesh3d` + `MeshMaterial3d` (walls, trims, caps, 28 pillars and 28 lamps, greenhouse frame and panes, benches, trees, alcove). `world.rs` creates about 44 `StandardMaterial`s (`materials.add`, `toon`, `glow`, `textured`, `state_mats`); `fx.rs` adds one per particle kind and `setup` adds 6 more (4 spell glows, bronze, gold).
- **Bevy already batches the draws; the cost is GL state calls.** The planner counted WebGL2 calls per frame by wrapping `WebGL2RenderingContext.prototype` (1280×720, headless, 1x):

  | tier | GL calls / frame | draws (`drawElementsInstanced` + `drawArraysInstanced`) | top calls per frame |
  |------|------------------|------|------|
  | `?low` | **2 045** | 44 | `texParameteri` 463, `bindSampler` 249, `bindTexture` 233, `activeTexture` 233, `disable` 152, `bindBuffer` 132, `bindBufferRange` 75, `vertexAttribPointer`/`Divisor`/`enableVertexAttribArray` 75 each, `framebufferTexture2D` 40, `bindFramebuffer` 23, `useProgram` 23 |
  | default | 4 600 | 103 | `texParameteri` 924, `disable` 546, `bindSampler` 496, `bindTexture` 463, `framebufferTexture2D` 220 |

  So under `?low` each draw costs about 46 GL calls, mostly texture and sampler rebinding (about 10 `texParameteri` per draw) when the material bind group changes. Each call is a wasm→JS crossing plus ANGLE validation, which matches the `wasm-to-js` heavy profile. Merging meshes would cut few draws; cutting **material switches and passes** cuts the calls.
- **Startup** builds two 64×64 procedural textures, the kit meshes and the whole courtyard in one `Startup` system. The load profile at 4x shows about 0.9 s in `__wbg_finalize_init` (wasm instantiate and start) and most of the rest in first-frame pipeline/shader compilation (`getShaderParameter`, `getProgramParameter`) and setup.
- **`publish`** builds the whole `__gameState` JSON every frame with `format!`, one `String` per object, then `join`. `hud.js` parses it once per HUD frame (about 30 ms of 40 s in the profile: negligible, so this item does not touch it).
- **Projectiles cannot tunnel.** `projectiles` moves each spell parametrically: `p.t += dt`, `a = min(p.t / p.dur, 1)`, `pos = from.lerp(to, a)` plus an arc. The target (`p.to`, `p.obj`) is fixed at cast time and the impact is applied when `a` reaches 1. There is no swept hit test, so a large dt only lands the spell in fewer frames. No projectile substeps are needed (test 7b checks impacts at large dt).
- **Pause is a game flag, not a paused clock.** The pause overlay sets `game.paused` (from `__gameIn.paused`); `Time<Virtual>` keeps running. `chem_tick`, `control` movement and `projectiles` return early while paused. So `Time<Virtual>` elapsed time is not a usable `gameTime`; A5 defines its own.
- **`?low` is a URL flag only.** `read_settings` sets `low` from `?low` alone; nothing selects it from hardware. `bars.md` defines B2's cloud half at `?low`, so that half is a proxy for weak hardware, not something a school Chromebook gets by default today. The direct player gain on slow machines in this item is Part A (the clock), which applies to every tier. Auto-selecting `?low` is filed as an idea row ("Out of scope").
- **`Player::step` cannot be unit-tested with plain `rustc --test`:** `player.rs` imports `bevy::prelude` (`Vec3`) and `world::{Aabb, Colliders}`. The client crate is its own workspace and is not in CI's `cargo test`. Test 3 therefore needs the integrator extracted into a pure module (A3).
- **`report`** logs `STATS ... entities=N ... wasm_mem_mb=X heap_live_mb=Y heap_peak_mb=Z` every 2 s. `heap` is a counting global allocator.

## Smallest version

### A. A game clock that matches the wall clock (correctness)

1. **New pure module `crates/bevy-client/src/clock.rs`** (no Bevy types, like `chem.rs`; `mod clock;` in `main.rs`):
   - `pub const MAX_FRAME_DT: f32 = 0.25;` This is the most game time one frame may advance. Below 4 fps the whole game slows evenly.
   - `pub const MAX_STEP: f32 = 1.0 / 60.0;` This is the longest single player-physics step.
   - `pub fn frame_dt(raw: f32) -> f32`: `raw` clamped to `[0, MAX_FRAME_DT]`. NaN, ±inf and negative values give 0.
   - `pub fn substeps(dt: f32, max_step: f32) -> (u32, f32)`: `n = ceil(dt / max_step)` with `h = dt / n`, so `n * h == dt`; dt 0 gives `(0, 0.0)`. n is capped at 64 as a guard.
2. **One clock for everything.** `main()` sets `Time::<Virtual>` `max_delta` to `MAX_FRAME_DT` explicitly (today it relies on Bevy's default), so `FixedUpdate` (chemistry) and the per-frame systems use the same ceiling. Every `time.delta_secs().min(0.05)` (4 in `main.rs`, 1 in `fx.rs`, plus any I-007 adds) becomes `clock::frame_dt(time.delta_secs())`. After this item, a grep for `min(0.05)` in `crates/bevy-client/src` finds nothing.
3. **Player substeps, with a pure integrator.**
   - New pure module `crates/bevy-client/src/motion.rs` (no Bevy types; `mod motion;` in `main.rs`). It holds the body of today's `Player::step` on plain data: `pub struct Body { pos: [f32; 3], vel: [f32; 3], grounded: bool, on_ice: bool }`, `pub struct Box3 { min: [f32; 3], max: [f32; 3] }`, and `pub fn step(body: &mut Body, target_h: [f32; 2], jump: bool, dt: f32, solids: &[Box3], ice: &[Box3])` with the same acceleration, jump, gravity and axis-by-axis push-out arithmetic, constants included. `pub fn advance(body, target_h, jump, dt, solids, ice)` runs `step` `n` times with `(n, h) = clock::substeps(dt, clock::MAX_STEP)` (jump only on the first substep). `motion.rs` may `use crate::clock` only through a path that also works under `rustc --test` (put the needed constants in `motion.rs`, or `#[path]`-include `clock.rs`).
   - `Player::step` becomes a thin wrapper: it converts `Vec3`/`world::Aabb` to `Body`/`Box3`, computes the wish target from yaw, calls `motion::advance`, and copies the result back.
   - `control()` builds the ice list and the `colliders.solid(chem)` list once per frame (as `Box3`), not once per step. The scripted `move` countdown uses the full `dt` once per frame.
   - Walking speed, acceleration (60 m/s² ground, 4 on ice, 12 in air), jump and gravity are unchanged.
4. **Everything else keeps its rate in wall time.** Cooldown 0.3 s, `cast_queue` expiry `0.3 + dt`, beam life 0.25 s, recoil decay 6/s, `caption_age`, projectile `t += dt` and particle emission `rate * dt` all now advance by the real (clamped) frame time. Emission probabilities such as `30 * area * rate * dt` can exceed 1 at dt 0.25; that only caps emission at one particle per emitter per frame, which is acceptable. Do not change it.
5. **State fields** (appended at the end of the `publish` JSON object, after every existing key): `gameTime` and `dt`. `dt` is this frame's `clock::frame_dt` value (4 decimals). `gameTime` is a game-owned accumulator in `Game`: `+= dt` each frame unless `game.paused`, reset to 0 by `reset` (3 decimals). It does not advance while paused. A tab refocus after a long stall advances at most 0.25 s of game time in one frame (0.05 s today); the player substeps keep that safe.
6. **Feel is unchanged at 60 fps and above.** At dt ≤ 1/60 the substep loop runs once with the same h, so movement and the jump arc are bit-for-bit the same. Below 60 fps the jump arc differs slightly from base, because each step is smaller. The existing golden `jump` check is the guard.

### D. Make perf runs valid and honest (perf lane, `tests/e2e/perf.mjs`)

1. **Frame-aware step timeouts.** A workload step waits until its predicate holds or until **both** 6 000 ms of wall time **and** 8 game frames (`state.frame`) have passed since it started. On a 3 s-per-frame software GPU a step can then last up to about 24 s, but it no longer drops a cast that the game will fire on its next frame. The `MAX_SAMPLE_S` cap still bounds the run.
2. **Machine load is recorded and gates validity.** Each run records `load_avg` (`os.loadavg()`: 1, 5, 15 min) at load start and at sampling end, plus `busy_procs`: up to 5 other processes above 50% CPU, sampled with `ps` at the same two moments (name and %CPU only; skipped with `null` where `ps` is missing). Unless `PERF_ALLOW_LOAD=1` is set, a run is invalid with reason `machine busy: load1=<x>` when the 1-minute load average at either moment is above `os.cpus().length * 0.5` (2.0 on the 4-CPU cloud box), not counting the run's own browser. Before each configuration the script waits up to 60 s for the load to fall under that limit, logging `[perf] waiting for quiet machine`.
3. **p99.** `cpu_ms` gains `p99` (GS-5). The verdict is unchanged (B2 is still the median).
4. *(Removed in revision 2: heap fields in perf. The golden memory guard, test 9, covers leaks.)*
5. **GL call count (diagnostic, needed only for step B3).** `PERF_GL_COUNT=1` wraps `WebGL2RenderingContext.prototype` methods inside `pageHook` (the function `perf.mjs` installs with `page.addInitScript(pageHook)`), only when the flag is passed in, and reports `gl_calls {per_frame, draws_per_frame, top: {name: per_frame} (10)}` for each run. Like the other test hooks it makes the run invalid on purpose (the wrapper adds CPU), so it is never used for a verdict.
6. `--self-test` covers the new pure helpers: the step-timeout rule, the load gate (`loadGate(load1, cpus)`), `p99` through `pct`, and the re-run rule (`rerunPlan`) from test 12.
8. **Logged re-runs.** A run that is invalid only for an environment reason (`machine busy`, throttle not verified) is re-run up to 2 times per configuration, each attempt logged in the JSON under `reruns: [{config, reason}]`. A run invalid for `workload_ok` false is never re-run (that is a product signal). The perf lane reads `state.frame` as it already does (`JSON.parse(window.__gameState).frame`, inside `pageHook`) and parses `STATS` lines with its existing `/STATS .*<field>=([\d.]+)/` pattern; it does not need to read the client.
7. `docs/loop/mac-perf.md`: no change needed, unless the field list in step 6 should show `cpu_ms.p99`. If it changes, the existing self-test lint of that file must still pass.
